# 部署手册

本文面向运维/实施人员，说明如何把这套系统部署到现场的工控机上。

---

## 1. 组成部分

| 组件 | 二进制 | 部署位置 | 数量 |
|---|---|---|---|
| 中心服务 | `igh-server` | 厂区服务器 | 1（可做双机热备） |
| 边端服务 | `igh-edge` | 每个工位工控机 | 每工位 1 |
| Web 前端 | `web/dist/` | 由中心服务托管 | — |
| 数据库 | PostgreSQL | 中心服务器 | 1 |

工位划分（按站点类型）：

| 类型 | 典型边端编码 | 说明 |
|---|---|---|
| `winding` | `edge-winding-01` | 落筒 |
| `sorting` | `edge-sorting-01` | 外检打标 |
| `packaging` | `edge-packaging-01` | 打包堆垛 |
| `warehouse` | `edge-warehouse-01` | 出入库 |

## 2. 构建

```powershell
cd E:\WorkSpace\IGH_Dev\igh-platform

# 后端
go build -o bin\igh-server.exe .\cmd\server
go build -o bin\igh-edge.exe   .\cmd\edge
go build -o bin\siteimport.exe .\cmd\siteimport
go build -o bin\hactl.exe      .\cmd\hactl

# 前端
cd web
npm ci
npm run build      # 产物在 web/dist/
```

前端产物有两个去处，`make web-build` 会一次拷到这两处：

| 去处 | 谁托管 | 什么时候用 |
|---|---|---|
| `<配置目录>/ui/` | 中心服务（`igh-server`） | 管理端页面，改一个文件不用重编二进制 |
| `internal/edge/app/dist/` | 编进 `igh-edge` 二进制 | 边端工位页面，现场断网也能打开 |

中心服务启动时会检查 `<配置目录>/ui/index.html`：

- 存在 → 域内所有非 `/api/`、非 `/ws` 的路径都回落到 `index.html`，支持 `/admin/production` 这类前端路由直接刷新
- 不存在 → 只打印一条警告，服务照常启动，根路径返回 404（适用于外部 nginx 托管前端的部署方式）

`<配置目录>` 是 `--config` 指定的目录，例如 `--config ./configs-dev3` 对应 `configs-dev3/ui/`。

**管理端与边端是同一个前端工程**，靠服务端注入的 `window.__IGH_EDGE__` 区分：

- 中心（无此变量）→ 注册完整路由：看板、工位、管理后台
- 边端（注入 `{type:"winding"}` 等）→ 只注册本工位页面，访问其他路径一律重定向回来

因此**不要试图从边端打开 `/admin`**：边端没有 `/api/v1/auth/login`，页面会直接跳回工位页。

## 4. 中心服务

### 4.1 配置

`<配置目录>/project.yaml`：

```yaml
project:
  name: "华祥智纤（九江）"
  timezone: "Asia/Shanghai"

server:
  http_port: 8099
  ws_port: 8102
  api_key: "<改成强密钥，边端要用同一个>"

database:
  host: "127.0.0.1"
  port: 5432
  name: "igh_platform"
  user: "igh"
  password: "${DB_PASSWORD}"     # 从环境变量读，不要写明文

modules:
  winding: true
  quality: true
  warehouse: true
  packaging: true
  erp: false                     # 见第 7 节
```

### 4.2 启动

```powershell
$env:DB_PASSWORD="<数据库密码>"
.\bin\igh-server.exe --config .\configs --log-level info
```

| 参数 | 说明 |
|---|---|
| `--config` | 配置目录，默认是二进制同级的 `configs/` |
| `--log-level` | `debug` / `info` / `warn` / `error` |

启动成功的标志：


## 5. 边端服务

### 5.1 配置

从模板复制并改：

```powershell
copy configs\edge-templates\winding.yaml <边端配置目录>\edge.yaml
```

必改项：

```yaml
edge:
  id: "edge-winding-01"        # 全局唯一，中心靠它识别
  type: "winding"              # winding / sorting / packaging / warehouse
  data_dir: "./data"           # 本地 SQLite 目录，离线时缓存事件

  server:
    url: "http://<中心IP>:8099"
    api_key: "<与中心 project.yaml 的 api_key 一致>"

  line:
    code: "L01"
    name: "卷绕线01"

  bobbins_per_doff: 8          # 必须有：一次落筒产出的锭数
```

> `bobbins_per_doff` 缺失时边端会拒绝产生所有落筒事件，并在日志里报 error。
> 取值见 `<中心配置目录>/production_lines.yaml` 中对应线路的值——**不同线路不同，不要猜**。

### 5.2 启动

```powershell
.\bin\igh-edge.exe --config <边端配置目录> --log-level info
```

启动成功的标志：

```
plugin loaded  type=winding
database migrated
registered with server
sync engine started  heartbeat_sec=10 sync_sec=30
```

### 5.3 注册

边端首次启动会自动向中心注册。中心侧可以在「设备管理」看到，或者在库里查：

```sql
SELECT code, status, last_heartbeat FROM edge_nodes;
```

`last_heartbeat` 每 10 秒刷新一次。**为空说明它从没连上过中心**。

## 6. 现场配置下发

边端启动后，中心会通过心跳把该边端的现场配置（点表等）推下去。

**配置不会自动生效**，必须在边端页面点「应用配置」：

```
http://<边端IP>:8080/  →  现场配置  →  应用配置
```

或者：

```powershell
curl.exe -X POST http://<边端IP>:8080/api/v1/edge/config/apply
```

成功的标志（边端日志）：

```
site config staged, waiting for operator confirmation  version=1 plc_devices=8
site config applied  version=1
```

之后边端心跳上报的版本号会变成 1，中心停止重发。

详细填写方法见 [现场配置指南.md](./现场配置指南.md)。

## 7. ERP 集成（可选）

### 7.1 现状

ERP 对接有两条路径，配置在 `<配置目录>/erp/integration.yaml`：

| 模式 | 行为 |
|---|---|
| `disabled`（默认） | 完全不推 |
| `push_only` | 直连 ERP 数据库写入 |
| `bidirectional` | HTTP POST 到 ERP 接口 |

**目标库是 MySQL 5.7**（旧系统 fangsi 库，`10.30.30.144:3306`）。

### 7.2 启用前必须做的事

1. **配置凭据**（用环境变量，不要写明文）：

```powershell
$env:IGH_ERP_DB_USER="fangsi_user"
$env:IGH_ERP_DB_PASSWORD="<密码>"
```

2. **核对字段映射** `<配置目录>/erp/mapping.yaml`

这份文件决定"新系统的哪个字段写进 ERP 的哪一列"。上线前必须逐列核对，尤其是 `key`（幂等主键）不能填错。

3. **确认推送表清单** `integration.yaml` 的 `tables`

fangsi 库只有 `doffings` / `trolleys` / `modules` 三张表。**不要加不存在的表**——推过去必然失败，只会把队列填满。

### 7.3 验证

```powershell
# 看当前模式与队列
curl.exe http://<中心IP>:8099/api/v1/erp/status
curl.exe http://<中心IP>:8099/api/v1/erp/queue?status=failed
```

队列项状态含义：

| status | 含义 |
|---|---|
| `pending` | 待推送 |
| `sent` | **对端已确认收到** |
| `failed` | 推送失败，`error_message` 里有原因 |

**看到 `sent` 才代表真的推过去了。** 早期版本存在"只打日志就标记成功"的问题，已修复——如果发现 sent 但 ERP 没数据，说明是历史遗留记录。

## 8. 高可用（可选）

中心和边端是**两套不同的机制**，别混：

| | 中心 | 边端 |
|---|---|---|
| 仲裁方式 | etcd 租约（Raft 多数派） | UDP 心跳（9999 端口） |
| 执行程序 | `hactl` | 边端进程内 |
| 数据库 | PostgreSQL 同步复制 | 各边端本地 SQLite 排队 |
| 虚拟 IP | 不用 | 预留 |

### 8.1 中心双机

**前提条件（缺一不可）：**

1. 3 个 etcd 节点（2 台服务器 + 1 台见证节点，见证节点可复用某台边端 PC，只跑 etcd 不跑业务）。Raft 多数派 = 2/3，才能容忍任意 1 个故障。
2. PostgreSQL 主备同步复制，`synchronous_commit = remote_apply`。
3. 两台服务器各跑一份 `hactl`。

**配置**：`configs/ha/cluster.yaml`，先校验再启动：

```powershell
hactl -config configs/ha/cluster.yaml -validate
hactl -config configs/ha/cluster.yaml -node server-a -run
hactl -config configs/ha/cluster.yaml -node server-b -run
```

`-status` 可以随时打印当前角色与数据库状态，**同样必须带 `-node`**（参数校验在分支判断之前，只给 `-status` 会直接报错退出）：

```powershell
hactl -config configs/ha/cluster.yaml -node server-a -status
```

`-node` 只能填 `server-a` / `server-b`，填见证节点会被拒绝。

**核心原则：能否写入由"是否持有 etcd 租约"决定，不由"数据库连不连得上"决定。** 网络半开（TCP 还连着但对端已死）时数据库层面判断不出来，Raft 租约可以。

决策表（`internal/shared/ha/quorum.go`，纯函数、有完整单元测试）：

| 租约 \ 数据库 | 主库 | 备库已追平 | 备库未追平 | 未知 |
|---|---|---|---|---|
| 持有 | 服务 | 提升 | 等待 | 等待 |
| 丢失 | **围栏** | 等待 | 等待 | 等待 |
| 未知 | **围栏** | **围栏** | **围栏** | **围栏** |

三条不可违反的规则：没有租约就不能写；租约状态未知一律围栏；只有追平的备库才能提升。

**时间预算：10 秒**，由代码里的 `ha.DefaultSwitchBudget()` 给出：租约到期 5s + LSN 检查 1s + 提升 2s + 中心重连 1s + 边端重试 1s。`cluster.yaml` 里的 `budget` 段目前**没有代码读取**（`ClusterConfig` 没有对应字段，`yaml.Unmarshal` 会静默忽略），改了不生效，以代码为准。这是设计预算，**尚未在真实三节点环境实测**。

**中心自动跟随主库（已实现）**

`igh-server` 通过 `GET /health` 上报两条信息：`ha` 段是 HA 配置回显，`database` 段是当前真实连接的库：

```json
{"database":{"multi_host":true,"primary":"172.22.0.6:5432","healthy":true,"generation":1,"error":""}}
```

`generation` 每跟随一次主库切换 +1，运维据此判断"到底切没切过去"。

启用方式：把 `configs/project.yaml` 的 `database.host` 换成 `database.hosts` 列表。

```yaml
database:
  hosts:
    - "192.168.10.1:5432"    # 初始主库
    - "192.168.10.2:5432"    # 初始备库
  port: 5432                 # 列表里没写端口时的缺省值
```

机制分两层，缺一不可：

1. **建连阶段**：连接串带 `target_session_attrs=read-write`，按列表顺序尝试，自动跳过备库与被围栏的旧主库（它们连得上、能读，但写入会失败）。
2. **复用阶段**：每 2 秒探测一次 `pg_is_in_recovery()` 与 `inet_server_addr()`；地址变了就递增代际号，池里的旧连接在下一次被取出时作废重建。

第 2 层是必须的：数据库切主后，连接池里已有的连接**不会**因为对端变成只读而失效，`database/sql` 会继续拿来用，应用层就会持续写入失败直到进程重启。

**实测（本机 ha-sim，2026-11-09，两次独立运行）：** 强杀主库 → 中心识别到新主库耗时 **5.1～5.3 秒**。期间日志先记录两次探测失败（备库此时还是只读），第三次发现地址变化并作废连接池；随后写入恢复并落在新主库。

注意这个 5 秒只覆盖"hactl 已把备库提升完、中心完成重连"这一段。端到端故障切换耗时取决于 hactl 的切换速度（实测 4 秒）+ 中心探测粒度（2 秒），两者叠加才是用户感知的停机时间。

**注意**：单地址配置（只写 `database.host`）行为与改造前完全一致，不启动监控、不做代际淘汰。多地址模式需要 `hosts` 里至少两台**都在** pg_hba 白名单内。

**仍未实现**：旧主库自动回退（`auto_rejoin_as_standby` 是空字段）。发生一次切换后，旧主库处于只读且时间线分叉，必须人工 `pg_rewind` 才能重新加入集群。

### 8.2 边端双机

边端同样支持 `active-standby`，用于边端工控机故障时接管。

**两台机器的 `priority` 必须不同**（数字小 = 优先级高）。优先级相同时双方都不会让位，结果就是两台都轮询同一个 PLC，一次落筒会产生两条事件。这个行为有测试固定（`TestEqualPriority_DoesNotFight`），不是 bug，是设计上的前提。

```yaml
# 主机
ha:
  mode: "active-standby"
  peer: "192.168.1.21"      # 备机 IP
  priority: 10

# 备机
ha:
  mode: "active-standby"
  peer: "192.168.1.20"      # 主机 IP
  priority: 20
```

**角色与实际行为是联动的**：降为备机时停止 PLC 轮询（保留连接），升为主机时恢复。若只改角色不停轮询，两台机器会同时读同一个 DB 块，每次落筒各上报一条事件——中心按 `(edge_id, event_id)` 去重，两台机器 `edge_id` 不同，**去不掉**。

启动时一律先轮询，不按"配置了主备"预先暂停：主机在启动前就挂了的话，备机收不到心跳也等不到提升，产线会一直没人读。

**实测切换耗时 6.5 秒**（判死阈值 6 秒 + 2 秒心跳间隔，最坏 8 秒），满足 10 秒要求。

**已知边界：** 上述 10 秒指标的前提是备机在暂停期间 **PLC 连接一直没断**。暂停期间连接若断开（例如 PLC 同时重启），PLC 主动重连的固定延时是 5 秒，且该延时在暂停状态下不会被提前触发。此时"切换 6.5 秒 + 重连 5 秒"约 11~12 秒，**会超过 10 秒**。这属于主机故障与 PLC 中断叠加的双故障场景，不在原指标覆盖范围内。现场若频繁出现 PLC 重启，建议等 PLC 恢复稳定后再做切换演练。

**排查用**：`GET /api/v1/edge/ha/status` 返回的 `listening` 字段为 `false`，说明心跳端口没绑上（通常是被占用），这台机器永远收不到对端心跳、永远不会让位。此时它的行为等同于主机。

## 9. 数据备份

需要备份的只有两样：

1. **PostgreSQL** —— 全部业务数据
2. **各边端的 `data/` 目录** —— 离线期间缓存在本地 SQLite 的事件

```powershell
# 中心库
docker compose exec postgres pg_dump -U igh igh_platform > backup.sql
```

边端的事件是"至少一次投递 + 幂等去重"，即使本地 `data/` 丢失，已上传的数据不会重复；但**未上传的会丢**，所以断网期间要备份。

## 10. 常见问题

**Q：边端启动报 `bobbins_per_doff 未配置，落筒事件将被拒绝上报`**
A：在 `edge.yaml` 的 `edge` 段顶层加 `bobbins_per_doff: N`，N 取线路主数据里的值。

**Q：边端连不上中心，一直重连**
A：检查 `server.url`、`server.api_key`、防火墙。边端在离线状态会继续采集并缓存在本地，恢复后自动补传。

**Q：中心日志刷 `pull failed ... status 404`**
A：边端在拉主数据但中心没有对应接口。检查中心版本是否与边端匹配——这是历史版本的问题，已在 `edge_sync` 路由补齐后修复。

**Q：`/api/v1/edge/sync/lines` 返回 500，报 `unsupported Scan`**
A：旧版本 `production_lines.config` 的 JSON 序列化问题，已修复（`gorm:"serializer:json"`）。确认用的是最新二进制。

**Q：包装/仓库的点表配好了但没数据**
A：先看边端日志有没有 `plc connect failed`。连不上 PLC 时不会产生任何业务事件，也不会污染数据库。检查 `host` 是否可达。

**Q：改了边端配置但重启后又变回去了**
A：边端启动时优先使用**已生效的现场配置**（`data_dir/site_config.json`），而不是 `edge.yaml` 里的点表。这是设计如此——否则现场改的东西一重启就丢。要改点表请通过中心下发 + 边端应用。

**Q：怎么确认某个边端用的是哪版配置？**
A：`curl http://<边端IP>:8080/api/v1/edge/config`，`version` 是已生效版本，`pending` 是待确认版本。
